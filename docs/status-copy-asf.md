# ASF mode: Steam account status following

This backend requires the separately installed **ASFStatusRelay 0.3.0 safe-field companion** through ASF's official IPC. It does not install a plugin, start a bot, open a new Steam CM session, attach to a game, or change Steam client files. The toolbox does not expose a generic ASF command console through this feature. Source and a manual build script are in `integrations/asf-status-copy/`.

The old 0.2 plugin is deliberately rejected: its small exclusion list could still publish server, room, session or join-token fields to Steam even if the toolbox filtered its UI report. Filtering only `STATE` is not a publication/privacy safeguard. Version 0.3 applies an explicit public allowlist at both source decoding and upload encoding. A strict `COPYCAPS` handshake is required before preview/start; no old plugin is silently treated as compatible.

## Required setup

- Install only the reviewed companion DLL manually using a matching ASF-generic version and .NET 10 runtime; .NET 10 SDK is needed only to build it. The toolbox does not update/restart the ASF service. Both accounts must already be configured, connected and logged on as **two distinct ASF bots**. Account 1 is the destination bot; account 2 is the source bot. Merely entering a friend's SteamID64 does not make that friend's private/source-session data available to this plugin.
- The destination bot name must resolve to exactly account 1's SteamID64. Exactly one other bot must resolve to account 2's SteamID64. Ambiguous aliases and mismatches are rejected.
- This computer must be logged in to account 2, not account 1. The current local AppID is the allowed-game authority. The plugin's selected source must additionally be confirmed by its source bot's own playing-session callback, not by a cached friend persona.
- IPC must be enabled and reachable, with sufficient ASF Owner permission for `RPRELAY CONFIG` and `RPRELAY APPLY`. Use HTTPS on an untrusted network. HTTP is accepted for an existing trusted/local deployment; no certificate bypass is installed.
- Use one controller for this plugin. Its configuration/session is global, not one independent relay per destination bot. There is **no lease, compare-and-swap configuration API, or controller identifier** in version 0.3, just as in 0.2. Configuration fingerprints prevent ordinary accidental replacement, but cannot make concurrent controllers atomic.
- The interval must be an integer from 15 to 120 seconds, matching the plugin's supported range. Keep the toolbox and ASF clocks synchronized; timestamps far in the future or too old are rejected.

## Start and follow

1. Send the read-only `RPRELAY COPYCAPS` command and require exactly `{"protocol":1,"safeFields":true,"groupIdentifiers":false,"groupSize":false,"sources":"registered-bots"}`. Then read `GET /Api/Bot/ASF`; bind the two exact bot names and SteamID64 values. Numeric UInt64 IDs are preserved without JavaScript rounding.
2. Read `POST /Api/Command` with `{"Command":"RPRELAY CONFIG"}`. Validate all five configuration fields: `MainBot`, `SourceBots`, `AllowedApps`, `StartupMode`, and `PollIntervalSeconds`.
3. An existing `On` task is never replaced, even with replacement consent. Replacing an existing `Off` or `Observe` route requires explicit consent. A malformed/unknown configuration is not treated as an empty configuration.
4. Save the previous valid non-`On` configuration in this backend's memory. Apply a single-source configuration with `StartupMode: "Observe"` and `AllowedApps: [currentLocalAppId]` using only `RPRELAY APPLY <base64-UTF8-JSON>`.
5. Read back matching `CONFIG` and `STATE`. Only the bound destination, exact selected source, expected mode and a fresh observation are accepted. Only then send `RPRELAY ON`, and read the configuration/state again. The backend never sends `START`, `VERIFY`, `SOURCE`, a shell command or a user-supplied command.

Before and after each IPC request, the backend rechecks the local source account, Steam process identity and expected AppID, plus the current toolbox operation. If account 2 is not playing, the feature waits. It does not clear or stop someone else's configuration. For an owned route, a game change follows `OFF -> APPLY Observe for the new AppID -> confirm source -> ON`. An externally changed mode or route is a conflict, not permission to turn it back on.

The preserved `STATE` schema does not expose the selected source SteamID, source AppID, activity epoch or a separate source read-success flag. It exposes `SelectedSourceBot`, `ObservedAt`, `RichPresence`, `ActiveAppId` and `LastUploadAt`. The backend therefore combines the exact bot roster binding, a single allowed local AppID and the plugin's source-session selection. `ActiveAppId` is zero in Observe mode; it is not misrepresented as the source game. A fresh `ObservedAt` means the **plugin made an observation**, not that an independent peer confirmed the source or destination display. Empty observed fields may mean no published RP or an unavailable read; the UI must not call that verified rich presence.

## What is copied and what is not verified

- Only the explicit native-style public RP key allowlist and a valid `steam_display` token can be uploaded or reach the toolbox report. Connection/join/server/room/session fields, raw group IDs, group size, controls, overlong text, URLs, addresses and recognizable identifier-bearing join strings are rejected. This is conservative filtering, not a universal scanner for secrets disguised as arbitrary prose. Required game-specific fields outside the allowlist are omitted, which can prevent a localized template from rendering; nothing is fabricated to replace them.
- This plugin version explicitly excludes `steam_player_group` and `steam_player_group_size`. Asking for group-size copying fails with `COPY_ASF_GROUP_UNSUPPORTED`; it is not silently ignored.
- The plugin uses the destination bot's existing ASF `OnlineStatus`. The toolbox's `persona` preference cannot override it through this protocol and is not claimed to have done so.
- `LastUploadAt` means an upload was submitted. It is **not** peer confirmation. Reports always use `verification: "not-verified"`; the actual Steam friend display remains an external observation.

## Stop, restoration and failure

The backend retains the owned route fingerprint (destination/source names, allowed AppIDs and interval) privately. `StartupMode` is checked as a transaction state, not included in route ownership: `ON` itself persists it as `On`, and a lost ON response must not prevent a later safe OFF.

Stopping first cancels further work. It does not depend on local Steam, the now-cancelled toolbox operation, or the source bot remaining online: switching the local client back to account 1 or exiting Steam must not make a remote task impossible to stop. The backend uses its saved ASF connection, the destination bot's original SteamID64 and the owned non-mode configuration fingerprint. If that remote ownership still matches, it sends `OFF` and verifies `CONFIG`/`STATE`. The previous valid `Off` or `Observe` configuration is restored and read back when possible. A previous `On` task is never restored. Without a previous valid configuration, the new configuration remains `Off`; no bot is started. Stopping the relay does not claim that every pending ASF cleanup or every already-published Steam display has disappeared.

If the remote destination bot resolves to a different account, the remote route was changed, the request timed out, or OFF/restoration cannot be confirmed, stop fails with `COPY_STOP_UNCONFIRMED`. The backend retains the uncertainty rather than reporting success. Check ASF manually before allowing another controller. Each HTTP request has a ten-second bound, a one-MiB response bound and disabled redirects. Transport errors are replaced with fixed codes; URLs, passwords, raw RP and SDK error strings are not logged by this backend.

`OFF` stops **RPRELAY**, not the already logged-in ASF bot. It does not log out account 1, stop its bot, change its ordinary farming settings, or remove its existing Steam CM connection. Before switching the desktop Steam client back to account 1, manually stop account 1's ASF bot if that simultaneous login affects the desktop friend list. This feature cannot promise to eliminate the effects of an independently running, already logged-in ASF bot.

**ASF tasks can continue after toolbox crashes, network loss or forced termination.** Version 0.3 still has no expiring lease or controller identifier. A normal toolbox exit attempts OFF, but cannot promise it reached the server. In ASF's own console or trusted IPC, inspect the configured route and use `RPRELAY OFF` when needed; do not assume closing the toolbox stopped a remote task. If the toolbox process died, its in-memory previous-configuration/ownership record is lost: the next start refuses an already-On task instead of taking it over.

Before manually upgrading an existing deployment, send `RPRELAY OFF` through its trusted console/IPC and read `RPRELAY CONFIG` plus `RPRELAY STATE` to confirm it is stopped and the saved `StartupMode` is `Off` (or an intentionally selected non-publishing `Observe`). Only then replace the DLL and perform a controlled ASF restart. An old saved `On` configuration can otherwise resume automatically on restart. Do not fix this by copying another configuration or automatically rewriting the user's JSON; preserve the original configuration and verify the new plugin's `COPYCAPS` after restart.

## Verification boundary

Automated tests exercise fake IPC, capability negotiation/old-plugin rejection, bot/ID binding, consent, stale data, mode/config conflicts, app transitions, lost replies, stop failures, cancellation, timeouts and privacy filtering. The companion has new deterministic offline sanitizer/upload-boundary tests; no old captured fixtures or user configuration is included. These tests do **not** connect to a real ASF server or Steam account and do not establish live compatibility with a specific deployment. The companion preserves the prior generic CONFIG/STATE protocol while adding the safe publication policy; deployment is a separate explicit step. Its distributable contains only the new DLL and generic README, not old ZIP contents, JSON configuration or validation captures.
